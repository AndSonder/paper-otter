# 组织推理

数学推导或机制讲解写逻辑稿前读取；系统执行示例由入口直接链接。

从一个具体困难进入：已有方法在哪个操作或约束下不够用？读者为什么需要下面的结果？新增一个核心约束时，说明它在什么任务中有用；材料已有具体用途，就别只写“现在要求满足该约束”。可以由待保持的性质引出构造，也可以由一次失败的计算找出需要改变的量。不要为了“有故事”虚构失败、实验或个人经历。

段落应接住前面留下的问题。背景、变体和术语在真正需要时引入；文章开头提出的核心问题要及时兑现。顺序没有统一模板：可以先展示核心结果再解释，也可以跟着构造逐步发现。若先用一个假设推进，读者应知道它意味着什么，何时会得到一个实际可用的实例。

构造能满足条件，不等于它由这些条件唯一决定。解释“为什么这样选”时，区分可行构造、启发式选择与唯一结论。不要把方法有效的实验观察写成公式已经证明的收益。

系统论文要跟踪一个具体块、请求或设备：数据在哪里，什么时候就绪，谁等待谁，一步结束后保存什么，下一步如何接续。再据此说明省去了哪次搬运、哪段等待，新增什么代价。若结论依赖某种执行顺序，要给出支撑结论的顺序与就绪关系，不能只说图中存在可行构造。涉及工程代价时，交代原有执行方式需改变哪些职责，不必扩成实现教程。只有“重叠、融合、复用”这些名字，读者仍看不到机制。修复示例见 [references/explanation-patterns.md](explanation-patterns.md)。

符号首次出现说明含义；矩阵写清形状或索引，别让同一个词在中途换对象。重点展开第一次改变表示、依赖条件或近似方式的步骤。引用定理可以，但若它正是核心疑问，至少解释适用范围内的来由或关键一步，不能给它起一个名字就算解释过。特例用于理解和校验，不冒充一般证明。

公式前让读者知道正在算什么，公式后推进新的理解，避免再把同一式子逐字读一遍。能沿用已有关系解决问题，就不另立一套符号；必要的新知识则就地讲清，不把术语当桥梁。

例子要有明确作用：展示一种变化、排除一种误解，或让操作过程可见。数字要真能区分正确机制与错误办法；均匀、对称或约消可能掩盖差异。自造算例用“假设”或“例如，取……”自然引入，让读者分清算例与实测，不必反复贴“教学计算”的标签。删掉一个例子前，确认它原本解释的事情仍有正文依据；别因另一段公式更完整，就丢掉不同的解释作用。

递推明确每个对象分别保存哪些状态；概率公式说明期望针对谁；张量实现核对归一化轴、掩码和极限。数学等价与浮点逐位一致分开，推理常驻状态与训练峰值显存分开。涉及总量时，把项对应到实际张量、运算或等待事件；引用论文系数与本文自行推导也要分清。

前提放在它影响的步骤附近，讲清违反时会改变什么。严格结论、近似、直觉、实验和猜测不能混在一起；但同一个限制通常解释一次就够，后文只有进入新情形才再展开。不要让“不能说明什么”的反复声明挤掉“现在能判断什么”。完整配置、来源核查过程放在证据文件，正文保留决定理解和判断的条件。

修订长推导时，检查每段实际增加了哪个理解：它解决了什么未解决的问题，后文在哪里需要这个结果？若两段只以不同工具证明同一结论，通常择一；另一条路线只有带来后文需要的新认识才展开。比较路线时也考虑新工具在后文能否复用，不以证明短或抽象层次高作为优点。必要的关键推理仍须完整。主线混乱时可把相关段落各概括一句，检查实际衔接，不需另交固定格式提纲。

引入新对象时，先接住读者已经理解的关系，再说明尚缺哪一步、新对象如何补上。不能仅用“因此”“进一步”掩盖缺失的因果。长计算结束后说明现在能判断什么，不再逐字复述公式。
