# 修复“看上去正确但读不懂”的段落

以下均为原创教学示例。选择适合读者卡点的做法，不套用固定句式。

## 从操作困难引出设计

只有知识点的段落：梯度分桶支持通信与计算重叠。小桶可以更早发起通信，但通信次数增加，因此桶大小需要权衡。

可以跟着推理的解释：反向传播逐层产生梯度。假如把所有梯度装进一个桶，第一层算完的那份也得等到最后一份就绪，整个桶才能开始通信。这段时间里，通信链路本来可能在工作，却没有拿到任务。

于是先把已经就绪的一部分交给通信，让反向传播继续计算剩余梯度。这样拆桶的理由不是“小更好”，而是不必让早已就绪的数据等待还没算出的数据。不过，每发起一次通信也有固定开销。如果桶继续缩小，提前开始所省的等待可能被更多次启动消耗掉。选择桶大小时，需要比较这两段时间，而不能只看每桶的数据量。

这里先跟踪同一份梯度为何等待，再由等待引出分桶，最后让新操作带来新的限制。第二段不是对第一段换一种说法，而是回答它留下的问题。实际性能还依赖实现与硬件；没有测量时不编造最佳桶大小。并非每篇都需要反例或三段结构；已有推导能自然产生下一步时，直接保留它。

## 将性能形容词换成可追踪的操作

薄弱段落：算子融合减少内存访问，改善数据局部性，从而提升效率。

具体解释：设第一个算子生成一个中间张量，第二个算子随即读取它。分开执行时，中间结果需要写入显存，再被读回；如果两个算子能在同一个kernel里完成，而且中间结果能留在片上存储，这一写一读就有机会省掉。但融合后的寄存器需求也可能上升，限制同时驻留的工作量。因此，少搬一份数据是收益来源，是否更快还需要看融合后的资源占用和实际耗时。

修复点：明确搬运的对象、发生的次数、替代路径和新增代价。对不满足片上容纳条件的情况，不沿用同一结论。

## 用约束说明公式为何长这样

给一个构造公式前，先说它必须保持的性质；代回一个熟悉的特殊情形，检查是否退化到原方法。若构造满足性质但不唯一，说清“这是一个可行构造”，不要宣称从条件唯一推出。公式自身不能证明训练收益。

## 选择真正能区分两种理解的例子

若两种算法在均匀输入上碰巧得到同样答案，均匀例子不能解释它们的差别。改变一个条件，算出分歧，随后从一般表达式解释哪个量决定分歧。不要堆三四个结论相同的例子。

## 在需要的层级补推理

对熟悉微积分而不熟悉矩阵求导的读者，可以展开一个分量并标明索引，再回到矩阵形式。无需把整篇改成不含公式的比喻，也无需把每个初等代数步骤全部拆开。真正需要展开的是第一次改变表示方式、近似或依赖条件的那一步。

## 给边界一个具体后果

薄弱段落：该方法存在一定局限，实际应用需要综合考虑。

具体解释：这个等式只覆盖常驻状态。如果执行中还要临时拼出完整张量，那么常驻状态减少并不能直接推出峰值同倍下降。判断设备是否装得下，应把临时张量活跃的时间区间也算进去。

边界应回答“哪一项推理会失效、结果如何改变”。与正文结论无关的风险列表移走。
